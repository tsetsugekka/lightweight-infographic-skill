# 轻量信息图

用少量文字、具体的小插图和清楚的关系线，让读者看懂产品如何工作。保留轻量的设计语言，按内容调整布局；不要把历史项目的图标、功能和箭头当成通用模板。

## 输入与事实

从用户提供的说明、仓库文档、代码或参考图中明确：要解释的核心问题、读者、展示位置、语言、尺寸和所需格式。已有信息足够时直接推进；只询问会实质改变内容或交付方式的缺口。

- 以实际资料核对名称、功能、数据流和使用条件；风格参考只决定视觉，不证明功能存在。
- 用一句话确定这张图要让读者明白什么，再提炼主线。常见顺序流程可以是 3–5 步，但架构关系、并行分支和循环应采用合适结构，不强行改成线性流程。
- 每个环节保留短标题、1–2 行通俗解释和承担解释作用的小插图。次要能力可作为辅助区，技术细节移至图外正文；影响理解的条件留在相关环节附近。
- 箭头连接真实作用的对象。反馈、可选能力和必经步骤要能区分，不能为闭环美观而改变因果或把“可能可用”画成保证成功。

## 视觉语言

- 白色或近白背景，低饱和浅蓝、浅绿、浅杏、浅粉等分区；按含义分配颜色，不必用满。标题近黑、正文深灰，阴影和渐变仅作轻微层次。
- 让图示解释动作或对象：用来源列表解释收集，用分类清单解释整理，用状态界面解释检测，用结果预览解释输出。避免每块只换一个图标、其余全是文字。
- 图标和小型界面保持统一线条与细节密度。使用项目现有且允许使用的标识，名称与产品、插件等后缀准确；不要把别的项目的标识、波形或播放器固定带入新图。
- 标题、步骤标题、正文、注释形成清楚层级。留足内边距，优先改写和换行，不能靠缩小到难读解决溢出。不同语言分别排版，不机械替换字符串。
- 主流程常用实线箭头，反馈常用较轻虚线；其他关系选合适连线，必要时加简短标签。避免交叉、穿字、悬空或方向不明。
- 横版、竖版或分层结构由内容和展示空间决定。README 按常见正文宽度检查；PPT 按目标页面比例和实际观看尺寸检查，常见宽屏可从 16:9 起步。
- 把空间留给解释性的图示，控制页眉与空白比例。页脚按需要放自然的项目标识或短定位；不机械添加“依据 README 整理”“仅为流程示例”等制作套话。必要事实边界写在对应内容旁。
- 避免强渐变、霓虹、大面积深色科技背景、玻璃质感、装饰性 3D、电路线与悬浮光球。

## 画布比例与手机竖版

- README 沿用适合内容的横版比例；PPT 按目标幻灯片比例。手机图文平台（如小红书）可用 **2:3 竖版**，例如 1200 × 1800 或 1024 × 1536。这是本 Skill 的设计预设，不代表平台强制规格；用户指定比例优先。
- 用户说“横纵比反过来”时，交换原画布宽高：3:2 → 2:3，16:9 → 9:16。重新排布图文和连接线，不旋转成品、不拉伸，也不直接把横向多列缩到竖图里。
- 竖版通常采用从上到下的 3–5 个模块，每个模块可用左文右图或交错图文，按内容选择；保留主线和必要辅助关系，不强制某种版式。标题简短，降低单页文字量；信息过多时按用户需求拆成多张。
- 给定 GitHub 仓库时，以准确的 **`owner/repo`** 标识来源；仓库名只在所属用户或组织下唯一，不能省略 owner 后当作唯一地址。用与整图一致的轻量仓库标识区呈现，例如 GitHub 图标、留白、对齐和清楚的文字层级；长标识可在 owner 与仓库名之间分层换行，不缩成难读小字、不仅在页脚堆一行裸文本。二维码是否加入按下节的场景默认规则决定。
- 四周可从约 5% 安全留白起步。标题、关键图示和必要说明放在安全区域，页脚不贴边；不为填满画布堆装饰。
- 导出后按约 360–430 像素显示宽度实际查看：步骤标题和正文无需放大也应可读，箭头方向清楚。若字太小，先删减或拆分内容，再调整图文比例。

## 制作与交付

根据当前工具和用户要求选择可实现的格式，不将某个专用服务设为前提。

- 需要精确文字、箭头、多语言维护或矢量源文件时，优先使用真实文字与独立图形对象制作 SVG 或幻灯片；需要自然插画时，可使用当前可用的图像生成工具。遵守当前环境对生成和编辑图像的工具要求。
- 用 PNG 交付便于直接插入 README 或 PPT 的展示图；用户需要维护时提供真正可编辑的源文件。将整张位图嵌入 SVG 不等于可编辑矢量图；SVG 也不等于原生可编辑 PPTX。
- 请求 PPTX 或需要原生可编辑幻灯片时，使用当前可用的演示文稿工具或 Skill；没有相应能力时说明实际可交付格式，不声称已完成 PPTX。
- 文件使用清楚的相对路径，如 `assets/how-it-works.zh-CN.svg`。多语言版保持相同事实和视觉逻辑，分别检查字宽、换行及字号。
- 图像制作本身不授权发布仓库、替换现有文档或删除旧图。用户已授权的范围内直接完成；更新 README 时补充适当替代文本和原图链接。
- 交付文件不嵌入个人身份元数据、凭据或本地绝对路径。事实来源可在随附说明中用公开链接或文件名记录。

## 二维码：按使用场景决定

用户明确指定的二维码要求优先；否则按以下规则处理，不能仅凭横版或竖版判断：

- **手机图文平台：默认不加二维码**，即使参考图中有二维码也不沿用；用项目名或完整 `owner/repo` 标识来源。
- **GitHub README、PPT、产品文档：有明确所属仓库时，默认加仓库二维码**。从用户提供的链接或当前项目已核实的 Git remote 确定公开可分享的仓库地址，目标通常是仓库首页；图是竖版也不改变此默认。
- 未找到明确仓库地址时，不猜地址、不复用示例地址；需要二维码才能满足交付时再询问目标链接。私有仓库地址不默认嵌入公开产物。
- 其他场景按用户要求或明确的扫码需求决定。

- 用真实目标地址编码生成二维码，不能把图像模型画出的黑白纹样当成可用二维码。
- 留出独立区域、足够对比度和静区，通常至少四个模块宽；标签优先放下方，按实际长度换行，不越界或遮挡码区。
- 在最终导出的图片上实际解码并与目标地址逐字核对；对预期展示尺寸也做检查。失败时调整尺寸或布局后重新验证。没有解码能力时明确报告“未验证”，不要声称已通过。

## 验收

渲染最终文件并在实际展示尺寸下查看，修正发现的问题后交付：

1. 不读长说明也能理解主线；小插图确实补充含义。
2. 名称、功能与箭头符合来源，关键条件和可选关系没有被删改。
3. 文字、标识与连线无裁切、重叠或溢出，语言字形和字号可读。
4. 若有二维码，最终导出图可解码且地址正确。
5. 打开交付文件确认格式与可编辑性符合承诺，公开产物无个人元数据或私有路径。

最终提供图片预览、文件链接及简短交付说明；只报告实际完成的渲染、检查和验证。若工具限制导致部分检查未完成，说明具体缺口。
